# くまっちボム！ (Phase1〜2 + VRM対応 + サイコロ6面ステージ + オンライン対戦/ランキング)

ボンバーマン系対戦アクションゲーム。本リポジトリは開発仕様書のPhase1
（ゲーム基盤）とPhase2（ゲーム完成：アイテム・AI・勝敗判定・UI・BGM・
効果音）に加え、Phase3のVRM対応（VRMモデルを自キャラの見た目に使う機能・
4方向表示）、バトルエリアをサイコロ状の6面立方体3Dステージにする大型
改修、敵キャラの色違いスキン統一・ローカルPVP、そしてSupabase(Realtime/
Postgres)を使ったオンライン対戦・対戦結果ランキングまでを実装したもの
です。

## 動かし方

ES Modulesを使用しているため、`file://`で直接開くとCORSエラーになります。
簡易サーバーを立ち上げてアクセスしてください。

```bash
npm run dev
# もしくは
python3 -m http.server 8080
```

ブラウザで `http://localhost:8080` を開いてください。

```bash
node test_round_d.mjs  # 「プレイできなくなった」不具合の再発防止(静的チェック)・オートマッチングの希望人数/AI補充人数の計算式検証
node test_round_e.mjs  # 「対戦開始押すとフリーズする」不具合の修正検証(偽Phaser環境でGameScene.create()/_applyMatchInit()を実際に実行)
node test_round_f.mjs  # 「アイテムが全然でなくなった」不具合の修正検証(_onBombDetonate内のアイテム破壊/出現の順序)
node test_round_g.mjs  # オートマッチングの「参加する」項目・スマホ向け画面調整(仮想十字キー/爆弾ボタン・レイアウト縮小率)の検証

node test_round_i.mjs  # スマホ画面に面がおさまるように調整・AI難易度緩和・横壁からも面をまたげるように変更した点の検証
node test_round_j.mjs  # 壊せないブロックの密な配置・VRM歩行ポーズ(手足の振り)・サドンデス爆弾・敗北時即終了・トップ画面/爆弾画像差し替えの検証
node test_round_k.mjs  # タイトル画面全画面化・選択項目の視認性向上・敵AI回避弱体化(escapeSearchDepth)・新アイテム「時限装置」(⏱リモート起爆)の検証
```

VRMの実際の読込・3Dレンダリングや、サイコロ6面ステージのThree.js描画は
ブラウザ側のWebGL/Three.jsに依存するため、Node上のユニットテストでは
検証できません（座標変換・面またぎロジックなど「見た目に依存しない
ロジック部分」はtest_cube.mjs等でNode上で検証済みです）。実機（ブラウザ）
で「ゲーム開始」してみて、自キャラの見た目が四角から差し替わるか、
立方体状のバトルステージが正しく表示されるかをご確認ください。

## 操作方法

ソロ（人間1人+AI）の場合:

- 矢印キー（↑↓←→）: 移動
- Space: 爆弾設置
- Esc: ポーズ

ローカル対戦(PVP・人間2人以上)の場合、同一キーボードでのホットシート
対戦として、プレイヤーごとに別々のキーを割り当てています
（`GameConstants.js`の`HUMAN_KEY_MAPS`）:

| プレイヤー | 移動 | 爆弾設置 |
| --- | --- | --- |
| P1 | 矢印キー（↑↓←→） | Space |
| P2 | W/A/S/D | F |
| P3 | I/J/K/L | U |
| P4 | テンキー 8/4/6/2 | テンキー0 |

Escによるポーズは誰が押しても全員一時停止する共通キーです。

タイトル画面の「ゲーム開始」→ロビー画面で「参加人数」（人間+AIの合計）・
「人間プレイヤー数」（1人ならソロ+AI、2人以上でローカルPVP。最大4人）・
AI難易度・制限時間（「制限時間なし」も選択可）を選んでから対戦を開始します。

## 現在の実装状況

### Phase1: ゲーム基盤

- [x] Phaser 3 環境構築（CDN読み込み、ビルドステップなし）
- [x] マップのランダム生成（毎試合、開始地点は安全地帯を保証）
- [x] プレイヤー移動（グリッドベース、壁・ブロックとの当たり判定）
- [x] 爆弾設置・約3秒後の爆発・十字方向の爆風・壁で停止
- [x] 爆弾同士の誘爆（連鎖爆発）

**仕様変更（3回目のフィードバック反映）**: 壊せない壁(HARD)は通り抜け
できません（従来通り移動を阻みます）。壊せる壁(SOFT/ITEM)は、👻(GHOST)
アイテムを取得しているプレイヤー（AIも含む）のみ通り抜けできます。未取得の
間はSOFT/ITEMブロックも通常の壁と同様に移動を阻む障害物です。爆風は
従来通り壊せない壁の手前で止まり、壊せるブロックに当たるとそこまで届いて
破壊し、そこで止まります。また、👻取得済みで壊せる壁の中に立っている間は
爆弾を設置できません（通り抜けられることを利用した安全地帯化を防ぐため）。

- [x] AI行動（爆弾回避・撃破チャンスの実行・積極的なブロック破壊・アイテム取得・
      追跡・簡易閉じ込め戦術、難易度別パラメータ）
- [x] 詳細な勝敗判定（残機→撃破数→抽選）・死亡順に基づく最終順位確定
- [x] UI強化（ロビー画面での対戦設定、HUDへの順位表示、リザルトの詳細スコア表）
- [x] 試合開始前カウントダウン（3・2・1・START）
- [x] BGM・効果音（Web Audio APIによる合成音。実音源への差し替えはSoundSystem.jsのSE_DEFINITIONS/BGM_DEFINITIONSを変更するだけでOK）

### Phase3: VRM対応（第一歩のみ）

- [x] タイトル画面の「VRM変更」から`.vrm`ファイルをアップロードできる
- [x] アップロード（または`assets/vrm/kumacchi.vrm`のデフォルト）したVRMを
      正面・背面・左・右の4方向からレンダリングし、移動方向(上下左右キー)
      に応じて見た目が切り替わるようにした（`VRMSystem.renderSnapshotSet`）

**現状の割り切り**（将来の改善ポイント）:

- ライブ3D表示・歩行アニメーションではなく「4方向ぶんの静止画スナップ
  ショット」を移動方向で貼り替える方式（見下ろし2Dグリッド上でリアルタイム
  3D表示するのは大掛かりになるため、Phase3の段階ではこの方式を採用）
- 斜め移動や振り向きモーション等の中間表現は無く、4方向のいずれかに
  瞬時に切り替わる
- アップロードしたVRM本体はブラウザのタブを閉じると消える（LocalStorageには
  ファイル名のみ保存。ファイルサイズの都合上、本体そのものの永続化は
  今後Supabase Storage等と連携するPhase4以降で検討）
- 敵AIの見た目は引き続きプレースホルダー（色付き四角）のまま
- Three.js / @pixiv/three-vrm はビルドに含めず、`index.html`のimport map
  経由でCDN(jsDelivr)から読み込む方式。CDNに繋がらない環境やVRMの
  パース失敗時は自動的に元の色付き四角にフォールバックする

**修正済み: 「VRM読み込み失敗: Cannot read properties of null (reading
'getImageData')」エラーについて**: このエラーは、VRMを描画する
`THREE.WebGLRenderer`のcanvas(`renderer.domElement`)を、そのままPhaserの
`textures.addCanvas()`に渡していたことが原因でした。1つのcanvas要素は
一度`'webgl'`コンテキストを取得すると二度と`getContext('2d')`を取得できない
仕様のため、Phaser内部の2D読み取り処理が失敗していました。
描画結果を独立した2D canvasへ`drawImage()`でコピーしてから使うように
修正済みです。

**修正済み: キャラの頭が見切れる問題について**: 以前はカメラ距離を
`モデルの最大寸法 × 1.5`という近似値で決めていたため、実際にはFOV(画角)
28度では縦方向のカバー率が約75%にしかならず、頭や足がフレームから
はみ出していました。モデルの縦横の実寸法とFOVから三角関数で必要な
カメラ距離を正しく逆算し、さらに余白(1.35倍)を持たせるよう修正しました。
これによりキャラは以前よりやや小さく、全身が見切れずに収まって表示され、
ゲーム内の表示サイズも少し小さめに調整しています。

**「VRMが表示されない」場合のデバッグ**: ゲーム画面右上に読み込み状況
（読込中/描画中/失敗理由）を小さく表示するようにしました。失敗した場合は
そこにエラー内容が出るほか、ブラウザの開発者ツール（F12）のConsoleタブにも
`[VRMSystem]`/`[GameScene]`のログが出ます。このサンドボックス環境では
Phaser同様CDNへの到達がブロックされておりThree.js/three-vrmの実読み込みを
確認できていないため、`index.html`のimport mapに指定したURL・バージョン
（`three@0.160.0`、`@pixiv/three-vrm@2`）が正しく解決するかは実機での
確認が必要です。表示されない場合は右上のステータス表示かConsoleのエラー
内容を教えていただければ、そこから原因を特定して修正します。

### サイコロ6面ステージ（バトルエリアの3D化）

「バトルエリアをサイコロ状の3Dにしてほしい」というご要望に対し、選択肢の中
から最も規模の大きい「本格的な6面ダイスステージ」を実装しました。

- バトルフィールドが立方体(サイコロ)の6面(FRONT/BACK/RIGHT/LEFT/TOP/BOTTOM)
  になり、各面が11×11マスの独立した迷路として生成されます（`CubeStage.js`）
- 面の端まで移動すると、隣接する面へ実際に「乗り越えて」移動できます
  （立方体を展開したときの折り目に沿った移動になる想定。`CubeTopology.js`の
  `CROSSING_TABLE`で全24通りの辺の対応関係を定義・往復整合性を検証済み）
- 各面の外周は基本的に壊せない壁(HARD)ですが、四隅とそこへ近づくための
  隣接1マス(計8マス)だけは壊せるブロック(SOFT)として開放されています。
  ここを爆弾で壊す（または👻取得済みならそのまま）ことで面の端まで到達でき、
  6面すべてを行き来できます。辺の途中からは面をまたげません（`CubeStage.
  _openFaceCorners`）
- 隅・approachマスを爆弾で壊すと、面をまたいだ先(隣接面)にある対応する
  マスも自動的に壊れます（`CubeStage.getMirrorCells`）。爆風自体は面を
  またいで伝播しませんが、この「隅だけは連動して開通する」仕組みにより、
  片側だけ壊して反対側が塞がったまま身動きが取れなくなる状況を避けています
- 自分がいる面が常に画面正面に来るよう、立方体側が回転します
  （`CubeRenderer.rotateToFace`。2026-07更新、詳細は後述）
- 描画はThree.jsで新規に行い（`src/systems/CubeRenderer.js`）、Phaser側は
  従来通りHUD・カウントダウン・ポーズ/タイトル/ロビー/リザルト画面のみを
  担当します（`index.html`の`#cube-canvas`がThree.js専用、Phaserのcanvasは
  透明にしてその上に重ねています）
- ゲームロジック（`Player`/`Bomb`/`Item`/`AI`）は見た目を一切持たず、
  「今どの面のどのマスにいるか」という状態だけを持つように書き換えました。
  `CubeRenderer`はその状態を毎フレーム読み取ってThree.jsのメッシュを
  生成・更新・破棄するだけの「シャドウレンダラー」です（ロジックと描画の
  分離。開発ルール9に準拠）

**v1時点の割り切り（既知の制限）**:

- 爆弾の爆風・誘爆は面をまたぎません（爆風は常に自分がいる面の中だけで
  完結します）
- AIの追跡・撃破チャンス判定・トラップ戦術は同じ面にいる相手/アイテムのみ
  対象です（面をまたいだ相手を狙うことはしませんが、アイドル時の徘徊移動は
  面をまたいで行われます）
- 各面のサイズは11×11マス固定です（`CUBE_FACE_COLS`/`CUBE_FACE_ROWS`）
- このサンドボックス環境ではCDN(Three.js/WebGL)への到達がブロックされて
  おり、実際のブラウザ描画を一度も確認できていません。座標変換・面またぎ
  移動などの「見た目に依存しないロジック」部分は`test_cube.mjs`で検証済み
  ですが、3D表示そのものは実機（ブラウザ）でのご確認をお願いします。もし
  表示崩れやエラーがあれば、右上のステータス表示やブラウザのConsole
  （F12）のエラー内容を教えていただければ修正します

**修正済み: 「まったく3Dになってないし1面しかない」問題について**:
以前はカメラを面の法線方向から完全に真正面(真上から見下ろす形)に配置して
いたため、カメラの視線とブロックの厚み・立方体の奥行き方向がほぼ平行に
なり、厚みが全く見えず、他の5面(実際はシーンに常に存在している)も画面に
入らず、ただの平面にしか見えていませんでした。カメラを面の法線方向と
面内の「上」方向を組み合わせた斜め上(仰角50度)に配置する見下ろし視点に
変更し、ブロックの厚みや立方体の辺、隣接面の一部が画面に映り込むように
しました。この変更で対象の面全体が画面内に収まること、および隣接する
面の一部が視界に入ることを、カメラの投影計算だけを取り出したNode
スクリプトで検証済みです(実際のブラウザ描画そのものはまだ未確認です)。

**修正済み: 「面をまたいで移動できない(1面しか使えない)」問題について**:
上記のカメラ修正とは別に、そもそも各面の外周が全てHARD(壊せない壁)の
ままだったため、プレイヤーが面の端のマスに一度も立てず、面をまたぐ移動
処理(`resolveMove`)が実際には一度も発動できない状態になっていました。
四隅とその approach マス(隅へ歩いて近づくための隣接1マス)だけを壊せる
ブロックとして開放し、そこを壊せば面の端まで到達して隣接する面へ渡れる
ようにしました(`test_cube.mjs`で、内側から歩いて近づき→approachマスを
破壊→隅マスを破壊→面またぎ、という実際のプレイ手順に沿った検証済み)。

**対応済み: 「AIが自爆しすぎる」問題について**: 原因は、爆弾は十字型に
爆風が伝播し爆弾のあるマス自身も爆風に含まれるため、爆弾の真上や爆風の
軸線上にいると、隣接する4マスは(爆風range≥1なら)ほぼ必ず爆風の届く
範囲に入ってしまう点にありました。「逃げる方向」を決める`_findSafeDirection`
が隣接マスだけを見る1マス先読みだったため、この状況では常に「逃げ場なし」
と誤判定し、AIがその場に立ち尽くして自爆していました(爆弾を置く前の
「逃げ道はあるか」の事前チェック`_hasEscapeRoute`は既にBFS化して正しく
判定できていたのに、置いた後の実際の逃避行動だけが1マス先読みのままだった、
という食い違いです)。`_findSafeDirection`も数マス先まで辿るBFSに書き換え、
角を曲がって回り込む経路を正しく見つけられるようにしました。あわせて、
危険地帯にいても回避に失敗する確率(`mistakeChance`)も全難易度で引き下げて
います。

**修正済み: 「通れない壁が隣り合わせで、端に爆弾を置いても隣の面が壊れず
移動できない」問題について**: 前回の修正で各面の隅・approachマスを壊せる
ようにしましたが、面をまたいだ先(隣接面)にある対応マスは依然として壊せる
ブロック(SOFT)のまま残っていました。爆風は面をまたいで伝播しない設計の
ため、隣接面側のそのマスは自分のいる面からは絶対に壊せず、👻(GHOST)取得
済みでなければ足を踏み入れることもできません。つまり自分側の隅を壊しても
反対側が塞がったままで、resolveMove自体は着地先を計算できてもisWalkable
チェックで弾かれてしまい、結果として「その面から一切移動できない」デッド
ロックになっていました。これを解消するため、隅・approachマスを爆弾で
壊した際は、面をまたいだ先の対応マスも(壊せるブロックであれば)自動的に
同時に破壊するようにしました(`CubeStage.getMirrorCells` +
`GameScene._onBombDetonate`)。これにより、端で1回爆弾を使うだけで両面が
同時に開通し、行き来できるようになります。`test_cube.mjs`で、隅・approach
マスと隣接面の対応マスが実際に1:1で対応していること、および連動破壊で
両側とも通行可能になることを検証済みです。

**修正済み: タイトル画面すら表示されない不具合について**: `#cube-canvas`
（Three.js用）と`.phaser-canvas`（Phaser用）を重ねて表示するために両方を
`position: absolute`にしたところ、親要素`#game-container`にサイズ指定が
無かったため、子要素が通常のレイアウトフローから外れて**コンテナ自体が
幅0×高さ0に潰れてしまい**、Phaserの`Scale.FIT`が「親要素のサイズに
合わせてcanvasの表示サイズを決める」ため、ゲーム画面全体（タイトル画面を
含む）が非表示になっていました。ヘッドレスブラウザでCSSレイアウトのみを
再現して検証し、`#game-container`にサイズ指定が無いと実際に0×0になる
ことを確認した上で、`#game-container`に`width:100vw; height:100vh`を
明示指定して解消しています。

**2026-07更新: 「サイコロが転がるように面が切り替わるようにしてほしい」
「もっと3Dに」「画面中央に大きく表示してほしい」への対応**:

- **カメラ固定＋立方体を回転させる方式に変更**: 以前は面が切り替わる
  たびにカメラ自体を別の面用の位置へ瞬間移動させていたため、画面が
  唐突に切り替わる見た目になっていました。今回、床・ブロック・
  プレイヤー・爆弾・アイテム・爆風の全メッシュを1つのグループ
  (`CubeRenderer._cubeRoot`)にまとめ、カメラは常に固定位置に据え置いた
  上で、面が切り替わる瞬間にこのグループ自体をクォータニオンで
  アニメーション回転(`CUBE_ROLL_DURATION_MS`=550ms、
  `CubeRenderer.rotateToFace`)させる方式に書き換えました。見た目としては
  「サイコロ本体が転がって別の面が正面を向く」演出になります。回転先の
  クォータニオンの導出式(`Q = Mdst * Msrc(面)^-1`)は、threeパッケージに
  依存しない手計算スクリプト`verify_cube_rotation.mjs`で、全6面について
  「回転後に面の法線・面内の上方向が固定カメラの目標軸に一致するか」を
  数値的に検証済みです。試合開始直後の初期表示はアニメーションさせず
  即座にその面を向けるようにしています(`CubeRenderer.snapToFace`。
  何も操作していないのに立方体がグルッと回って見えるのを防ぐため)。
- **画面中央に大きく表示**: カメラ距離を`CUBE_RADIUS*3.6`から
  `CUBE_RADIUS*2.8`に詰め、ステージ・キャラクターが画面内でより大きく
  見えるようにしました。
- **もっと3Dに見えるように**: 影(shadow map)を有効にし、メインの
  方向光に加えて逆側からの弱いフィルライトを追加しました。ブロックの
  立体感や、立方体が回転する際の陰影の動きが出て、以前より平面的に
  見えにくくなっています。
- **既知の制限**: 上記のカメラ・回転関連の数式は手計算スクリプトで検証
  済みですが、このサンドボックス環境ではThree.js/WebGLへのCDN接続自体が
  ブロックされているため、実際のブラウザでの見た目（回転アニメーションの
  滑らかさ、影の見え方、画面サイズ感）はまだ一度も確認できていません。
  実機でご確認の上、違和感があれば教えてください（`CAM_DISTANCE`・
  `CAMERA_ELEVATION_RAD`・`CUBE_ROLL_DURATION_MS`はいずれも定数化して
  あるので調整は容易です）。

### 敵キャラの見た目統一（色違いスキン）・制限時間なし・ローカルPVP対応

3つのご要望に対応しました。

- **敵キャラを全員同じキャラクターの色違いに**: これまで敵(AI)はプレース
  ホルダーの色付き四角のままでしたが、同梱のデフォルトVRM
  (`assets/vrm/kumacchi.vrm`、赤いくまのキャラ)を全ての敵AI・2人目以降の
  人間プレイヤーの見た目として使用し、`PLAYER_COLORS`
  (赤/青/黄/緑/黒/白)ごとにCanvas2Dの`filter`（色相回転・彩度/明度調整）で
  色違いにしています(`VRMSystem.tintSnapshotSet`)。VRM自体を色ごとに
  再レンダリングするのではなく、既にレンダリング済みの4方向スナップ
  ショット画像に対してCSSフィルタを適用するだけなので軽量です。自分
  (プレイヤー1)がカスタムVRMをアップロードしている場合はそちらが優先され、
  それ以外の全プレイヤーはデフォルトVRMの色違いになります。
  **注意**: `hue-rotate`等のフィルタ値は各色が「それらしく」見えるよう
  見積もった一次値で、実際のブラウザでの見え方（特に黒・白は色相回転では
  なく彩度/明度側で寄せています）はまだ確認できていません。実機で見て
  色味が違う・分かりにくい場合はフィルタ値を調整しますのでお知らせください。
- **制限時間の選択肢に「制限時間なし」を追加**: ロビー画面の「制限時間」
  ステッパーで60/120/180/300秒に加えて「制限時間なし」を選べるようになり
  ました。選択すると`timeLimitMs`に`Infinity`が渡り、BattleSystemの時間
  切れ判定が発生しなくなります（全滅や残り1人になるまで対戦が続きます）。
  HUDの残り時間表示も「制限時間なし」の場合は`∞`と表示されます。
- **ローカル対戦(PVP)対応**: ロビー画面に「人間プレイヤー数」ステッパーを
  追加し、1〜4人（かつ参加人数以下）まで指定できます。2人以上を選ぶと、
  同一キーボードでのホットシート対戦になります（キー割り当ては上記
  「操作方法」参照）。人間プレイヤー全員は同じ面(FRONT面)からスタートし、
  各自の開始地点周辺に個別の安全地帯が確保されます。カメラは引き続き
  プレイヤー1の面を追従表示します（v1の割り切り: 誰かが単独で他の面へ
  渡っても、画面はプレイヤー1のいる面のままです）。リザルト画面も複数人
  の人間プレイヤーを★印で表示し、勝者が人間なら「（プレイヤー）」と
  添えるよう対応しています。
  **v1時点の割り切り**: 画面分割はしていない共有1画面方式です。5人目
  以降の人間プレイヤー（キーボードの物理的なキー競合を避けるのが難しい
  ため）には未対応で、その分は引き続きAIになります。オンライン対戦
  ではなく、あくまで同じ端末・同じキーボードでの対戦です。

### Supabase連携: オンライン対戦・ランキング

「ランキングとPVPはsupabaseを使う」というご要望に対応し、Supabaseの
Realtime(Broadcast/Presence)を使ったオンライン対戦と、Supabase上の
テーブルへ対戦結果を送るランキング機能を実装しました。

#### セットアップ（プレイ前に一度だけ必要）

1. [supabase.com](https://supabase.com) で無料プランのアカウント・
   プロジェクトを作成する。
2. プロジェクトのダッシュボード →「SQL Editor」で、同梱の
   `supabase/schema.sql` の内容をそのまま実行する（ランキング用の
   テーブル`rankings`とアクセス権限(RLS)が作成されます。オンライン対戦
   自体はRealtimeのbroadcast/presenceのみを使うため、テーブルの追加は
   不要です）。
3. プロジェクトのダッシュボード →「Project Settings」→「API」で
   "Project URL" と "anon public"キー(新しいダッシュボードでは
   "Publishable key"と表記される場合があります)を確認し、
   `src/config/supabaseConfig.js`の`SUPABASE_URL`/`SUPABASE_ANON_KEY`に
   貼り付ける。

未設定のままでも、オンライン対戦・オンラインランキングの導線は
「Supabase未設定」の案内を表示するだけで、ローカル対戦(AI戦・同一
キーボードでのPVP)は従来通り遊べます(開発ルール8と同じフォールバック
設計)。ランキングも、Supabase未設定時はこの端末のLocalStorageに履歴を
残すだけの動作になります。

#### オンライン対戦（別々の端末・ブラウザから対戦）

タイトル画面の「オンライン対戦」から利用します。設計は「ホスト権威型」
です:

- 部屋を作った側(ホスト)の端末だけが、マップ生成・AI・爆弾・アイテム・
  勝敗判定というゲームロジック全体を実行します(ローカル対戦と全く同じ
  コードパス)。
- 参加した側(ゲスト)は、ホストから届く状態(約10Hzの周期同期
  `state`、爆風/アイテム取得などの単発`event`)をただ描画するだけです。
  自分のキー入力(矢印キー+Space固定)はホストへ送信するのみで、ローカル
  では移動処理を一切行いません。
- この設計により、参加人数が増えても各クライアントの手元のシミュレー
  ションが食い違う「デシンク」が原理的に起こりません(ホストの1つの
  結果を全員がただ描画するだけのため)。
- マップ(ブロック配置)は、ホストが生成した内容を対戦開始時に1回だけ
  ゲストへ送信して共有します(1面11×11マスを1文字/マスの文字列に
  エンコード、`NetworkProtocol.js`)。

手順: ホストは「部屋を作る」→表示された5文字の部屋コードを対戦相手に
伝える→参加者が揃ったらAI人数・難易度・制限時間を選んで「対戦開始」。
ゲストは「部屋に参加する」→伝えられたコードを入力→ホストが開始する
のを待つだけです。オンライン対戦は人間プレイヤー最大6人(サイコロの
面数と同じ、`MAX_ONLINE_PLAYERS`)まで参加できます(ホットシートの
ローカルPVPが最大4人までなのは、同じキーボードでのキー競合を避ける
ための制約で、オンライン対戦では各自が自分の端末で操作するため
この制約がありません)。

**2026-07更新: オートマッチング機能を追加**: 部屋コードを相手に伝える
手間なしに、自動的に他プレイヤーと組み合わせる「オートマッチング」を
オンライン対戦画面に追加しました。専用のマッチングサーバーは持たず、
固定の合言葉チャンネル(待合ロビー)に全員がpresenceで参加し、参加が
一番早い人が実際の対戦部屋を作成して他の参加者を招き入れる、
クライアント主導の簡易な方式です(`OnlineLobbyScene._startAutoMatch`
以降のメソッド、`NetworkProtocol.js`のオートマッチング関連関数)。
参加者が定員(6人)に達するか、最大待機時間(`AUTO_MATCH_WAIT_MS`=8秒)を
過ぎると、その時点のメンバーで対戦を開始します。待っても自分一人
だった場合はAI(`AUTO_MATCH_SOLO_AI_COUNT`=3人)を補充して対戦を成立
させます。**既知の制限**: 専用サーバーによる調停が無いため、ごく稀に
複数のクライアントがほぼ同時に「自分がリーダーだ」と判断し、別々の
対戦部屋を作ってしまう競合が理論上あり得ます(確定前に少し待って
再確認する`AUTO_MATCH_LEADER_CONFIRM_DELAY_MS`で発生頻度を下げては
いますが、完全には防げません)。カジュアルな身内向けの利用を想定した
割り切りです。

**v1時点の割り切り(既知の制限)**:

- クライアント側の入力予測(client-side prediction)は行っていません。
  ゲスト自身の操作も、ホストへ送信→ホストが反映→次のstate同期で反映、
  という経路を通るため、体感で1往復ぶんの遅延があります。
- 爆風による通信量抑制のため、破壊されたブロックの情報は「単発
  イベント」でのみ送っています。ごく稀にそのイベントが失われた場合、
  ゲスト側の画面にだけ壊れたはずの壁が残って見える可能性があります
  (ホスト側のロジックには影響しません。見た目だけの問題です)。
- 画面分割はしていません(全員が同じ1画面を、ホストのプレイヤー1視点で
  見ます)。
- 再接続・切断後の自動復帰は未対応です(通信が切れた場合はやり直しに
  なります)。
- 部屋コードには有効期限や一覧機能が無く、相手に直接伝える方式です。
- このサンドボックス環境ではSupabaseへの実接続そのものを確認できて
  いません。メッセージの組み立て・状態適用ロジック(何を・どんな形式で
  送るか、受け取った内容をどう反映するか)は`test_network.mjs`で
  Node上で検証済みですが、実際のRealtime接続・複数ブラウザでの対戦は
  実機でのご確認をお願いします。

#### ランキング

タイトル画面の「ランキング」から、Supabase上の`rankings`テーブルの
対戦ログを集計したランキング(勝利数の多い順、同数の場合は参考として
累計exp降順、上位20名)を表示します。対戦終了後、リザルト画面から
自動的に結果を送信します(AI戦・ローカルPVP・オンライン対戦いずれも
対応。オンライン対戦では「自分が操作していた1人分」だけを送るため、
参加者全員分が重複記録されることはありません)。タイトル画面の「設定」
からランキングに表示する名前を変更できます(未設定時は「プレイヤー」)。

**2026-07更新: 表示順を勝利数順に変更**: `rankings`テーブル自体は
これまで通り「1試合1行」の対戦ログのままですが(スキーマ変更は不要)、
表示用のランキング取得時にプレイヤー名ごとの勝利数(`rank===1`の行数)を
集計し、多い順に並べ替えるようにしました(`RankingSystem._aggregateWins`。
専用の集計テーブル/ビューは作らず、直近の対戦ログを広めに取得してJS側で
集計する方式です)。

**既知の制限**: 専用のバックエンド(サーバー)を持たず、ブラウザから
直接Supabaseへ書き込む構成のため、「本当に対戦した結果か」をサーバー
側で検証する手段がありません。カジュアルな身内向けランキングとしては
十分な設計ですが、悪意のある投稿を完全には防げない点をご了承ください
(詳細は`supabase/schema.sql`のコメント参照)。

### 2026-07更新: 右側HUDパネル・爆弾への1回猶予・アイテムの死亡ドロップ/爆風破壊/歩くだけ取得・👻半減・爆弾キック

「画面の上下はブラウザの大きさに合わせて、右側の空いている部分に各
プレイヤーの情報を表示してほしい」という要望を中心に、対戦の遊びやすさ・
バランスに関する複数のご要望へまとめて対応しました。

- **画面レイアウトをブラウザの実サイズに追従**: Phaser.Scale.FITから
  Phaser.Scale.RESIZEへ変更し、画面の上下が常にブラウザの高さぴったりに
  なるようにしました(レターボックス/余白なし。`main.js`)。タイトル・
  ロビー・ランキング・リザルト・ポーズ等の他の画面も、中央揃えの位置を
  固定値ではなく`this.scale.width/height`から動的に計算するよう修正して
  あります。
- **右側プレイヤー情報パネル**: 対戦画面の右側に固定幅のパネルを新設し
  (`ViewportLayout.computeBattleLayout`、`GameScene._createHud`/
  `_buildPlayerCards`)、3Dバトルステージ(`#cube-canvas`)は残りの左側
  領域だけに表示するようにしました。パネルには人間・AI問わず全プレイヤー
  ぶんのカードが並び、各カードには残機・爆弾所持数・爆風範囲・所持中の
  効果(👟👻💥🛡🛟)・現在の面・順位を毎フレーム表示します
  (`GameScene._refreshPlayerCard`)。
- **画像アイコンの表示**: 各プレイヤーのカードにも、3Dステージ上の見た目
  ですでに使っているVRMスナップショット(自分は素の正面向き、敵/AIは色調
  補正済みの正面向き)をそのままアイコンとして表示します
  (`GameScene._setPlayerCardIcon`。既存のcanvasをPhaserのテクスチャとして
  再利用するだけなので、VRMの再描画は発生しません)。
- **爆弾への1回だけの猶予**: 各プレイヤーは試合中1回だけ、爆風に当たって
  もライフを失わずに済むようになりました(`Player.hasBombGrace`/
  `takeDamage()`)。猶予を消費した際は専用の効果音(`bomb_grace`)が鳴り、
  消費後は短時間の無敵(1.5秒、連続被弾防止)を挟んで通常通りライフが
  減るようになります。無敵アイテム(🛡)とは別枠のため、両方を併用できます。
- **撃破時のアイテムドロップ**: プレイヤーはこれまでに取得したアイテム
  種別を`Player.collectedItemTypes`として記録するようになり、撃破された
  瞬間、死亡地点付近の空きマスに同じ種別のアイテムを落とすようにしました
  (`GameScene._dropItemsOnDeath`/`_findNearbyEmptyTiles`。死亡地点そのもの
  は直前の爆風で埋まっていることが多いため、幅優先探索で近い空きマスを
  探して配置します)。
- **アイテムは爆風で破壊可能に**: フィールド上に出現済みのアイテムが
  爆風の範囲に含まれていた場合、そのアイテムを破壊するようにしました
  (`GameScene._onBombDetonate`)。同じ爆発でブロックを壊して新しく出現
  するアイテムまで誤って壊してしまわないよう、判定は「爆発処理開始時点で
  既に置かれていたアイテム」だけに限定してあります。
- **歩いただけでアイテムを取得できるよう修正**: 移動キーを押し続けて
  連続移動している最中、アイテムの上を通過してもすり抜けて取得できない
  不具合を修正しました。原因は、移動中の見た目の補間フラグ(`isMoving`)が
  真の間は取得判定自体をスキップしていたため、連続移動中は取得判定の
  タイミングが一度も回ってこなかったことです。プレイヤーの論理位置
  (col/row)は移動開始と同時に移動先へ即座に更新される仕様のため、
  `isMoving`の状態に関係なくcol/row一致だけで判定するように変更しました
  (`GameScene._handleItemPickup`)。
- **壁抜け(👻)の出現量を半分に**: アイテムの出現種別選択をデータ駆動の
  重み付き抽選に変更し(`ITEM_SPAWN_WEIGHTS`、`GameConstants.js`)、👻のみ
  他の半分の重みにしました(`Stage.js`)。
- **爆弾キック(💥)アイテムを追加**: 💥アイテムを取得したプレイヤーが
  爆弾の置かれているマスへ向かって移動しようとすると、その爆弾を進行
  方向へ滑らせて移動させられるようになりました(`Player.canKickBombs`、
  `GameScene._moveOrKick`/`_tryKickBomb`、見た目のスライド演出は
  `Bomb.slideTo`/`getMoveProgress`)。爆弾は壁・他の爆弾・他プレイヤーに
  ぶつかる直前まで滑り、面をまたいだ蹴りは非対応です(v1の割り切り)。
  オンライン対戦でも、ホストが蹴った結果の爆弾位置は既存の周期的state
  同期で自然にゲストへ反映されます(`GameScene._applyStateMessage`。
  従来はid単位の追加/削除しか見ていなかったため、同じidのまま位置だけ
  変わる「蹴り」を反映できるよう、既存ミラーの位置を毎回更新する処理を
  追加しました)。

**v1時点の割り切り（既知の制限）**:

- このサンドボックス環境にはブラウザ/CDNアクセスが無いため、右側パネルの
  実際の見た目(レイアウト・文字の折り返し・アイコンの表示)やリサイズ時の
  挙動、爆弾キックのスライドアニメーションの滑らかさは目視確認できて
  いません。ロジック面(レイアウト計算・アイテム重み・猶予消費・キックの
  停止判定・空きマス探索アルゴリズム)は`test_round_c.mjs`でNode上で
  検証済みですが、実機での見た目のご確認をお願いします。
- 爆弾キックはAI(コンピュータ操作のプレイヤー)には未対応です。AIが💥を
  拾っても、現状は通常の壁扱いとして蹴らずに回避行動を取ります(人間
  プレイヤーのみ蹴れます)。
- 死亡地点付近に空きマスが十分に見つからない場合(周囲が壁で完全に囲まれた
  ごく特殊な状況)、ドロップできるアイテムの数がその分だけ少なくなります。

### 2026-07更新: 「対戦開始押すとフリーズする」不具合の修正

前回の更新(オートマッチング設定追加)の直後、対戦を開始するとフリーズ
する(操作を受け付けなくなる)という不具合が新たに見つかり、修正しました。

**原因**: `GameScene.js`の対戦初期化処理(ローカル対戦・AI戦・オンライン
対戦ホストの`create()`、オンライン対戦ゲストの`_applyMatchInit()`)は、
いずれも右側プレイヤー情報パネルの各カードを組み立てる
`_buildPlayerCards()`を、勝敗判定・残り時間を管理する`this.battleSystem`
を生成する**前に**呼び出していました。`_buildPlayerCards()`は内部で
`_updateHud()`→`_formatRemainingTime()`を呼び、`this.battleSystem.
timeLimitMs`を参照して残り時間を表示しようとするため、この時点では
まだ存在しない`this.battleSystem`のプロパティを読もうとして
`TypeError`が発生していました。対戦開始のたびに必ずこの例外が発生し、
`GameScene.create()`(または`_applyMatchInit()`)の処理がそこで止まって
しまうため、対戦開始ボタンを押しても何も起きず、画面がフリーズしたように
見える状態になっていました。

この不具合は、実は前々回の右側HUDパネル導入時から存在していたもので、
前回修正した「カウントダウンのSCREEN_WIDTH参照漏れ」よりも呼び出し順序が
早い箇所で発生していたため、実際にはそちらの修正よりも先にこの例外が
発生していました(=前回の修正だけでは対戦を開始できるようにはならず、
今回の修正で初めて解消されます)。

**修正**: `this.battleSystem`(または、ゲスト側の簡易ミラーオブジェクト)の
生成を`_buildPlayerCards()`より前に行うよう、処理順序を入れ替えました。
加えて、同種の「生成順序に依存する不具合」が今後別の箇所で再発しても
画面全体が止まってしまわないよう、`_formatRemainingTime()`に
`this.battleSystem`が未生成の場合のガード(例外を投げず`'-'`を返すだけに
する)を追加しました。

**再発防止**: 前回(`test_round_d.mjs`)の静的チェックはimportの消し忘れ
という不具合には有効でしたが、今回のような「メソッドの呼び出し順序」に
起因する不具合は、ソースコードを眺めるだけでは見つけにくく、静的な
走査でも検知できません。そこで今回、ブラウザ/CDNに依存しない最小限の
偽Phaser環境(`document`/`fetch`もスタブ化)を用意し、`GameScene.create()`/
`_applyMatchInit()`を実際にNode上で実行して例外が起きないことを確認する、
より実行時に近いテスト(`test_round_e.mjs`)を追加しました。ローカルAI戦・
ローカルPVP・オンライン対戦ホスト・オンライン対戦ゲストの4パターン全てで
検証しています。

### 2026-07更新: 「アイテムが全然でなくなった」不具合の修正

**報告内容**: 「アイテムが全然でなくなった。もっとでるようにしてほしい。」

**原因**: 前々回(HUDパネル導入と同時期)に追加した「アイテムは爆弾で壊れる
ようにしてほしい」への対応(`GameScene._onBombDetonate()`内の
`itemsDestroyedByBlast`によるアイテム破壊処理)が、実装時のコメントでは
「ブロック破壊ループより前にスナップショットを取る必要がある」と明記されて
いたにもかかわらず、実際のコードはブロック破壊ループ(壊したITEMブロックから
新しいアイテムを出現させる処理を含む)の**後**に置かれていました。

このため、ITEMブロックを爆風で直接壊して新しくアイテムが出現しても、その
アイテムは同じ爆風の範囲内に存在する以上、直後に実行される
`itemsDestroyedByBlast`の判定(「爆風が届いたマスにあるアイテムを壊す」)に
必ず該当してしまい、出現した直後の同じフレームでそのまま破壊されて
いました。結果として、同じ面でITEMブロックを直接壊した場合はアイテムが
実質必ず消えてしまい、隣接面へのミラー破壊(面をまたいだ先のブロック破壊)
で出現したアイテムだけがまれに残るという状態になっており、「アイテムが
全然でなくなった」という報告とちょうど一致する不具合でした。

**修正**: `itemsDestroyedByBlast`のスナップショット取得・破壊処理を、
爆風範囲の計算・爆風エフェクト表示の直後、かつブロック破壊ループ(新規
アイテム出現処理を含む)より**前**に移動しました。これにより、判定対象は
「この爆発が起きる前から存在していたアイテム」だけになり、この爆発
自身が壊したITEMブロックから新しく出現したアイテムを巻き込んで破壊
することがなくなります。既存の「爆発前から置かれていたアイテムを爆風で
破壊する」挙動自体は変更していません。

**検証**: 実際の`Stage`/`CubeStage`/`Explosion`/`Item`クラスと、偽Phaser
環境上でインスタンス化した実際の`GameScene`を使い、`_onBombDetonate()`を
直接実行して確認するテスト(`test_round_f.mjs`)を追加しました。(1)同じ
爆風でITEMブロックを壊した場合に新しく出現したアイテムが即座に破壊され
ないこと、(2)爆発前から置かれていたアイテムは従来通り破壊されること、
(3)修正後のコード順序がソース上でも維持されていること、の3点を確認して
います。修正前のコードに対して同じテストを実行すると(1)と(3)が実際に
失敗することも確認済みで、真に今回の不具合を再現・検出できるテストに
なっています。

### 2026-07更新: オートマッチングの「参加する」項目・スマホ対応

**報告内容**: 「オートマッチングで探してる相手に入る方の項目も作って。
スマホでもプレイできるようにスマホ用の画面調整してほしい。」

**オートマッチングの「参加する」項目**: 従来、オンライン対戦ロビーの
「オートマッチング」ボタンを押すと、必ず希望人数・AI難易度・制限時間を
選ぶ設定画面(`_showAutoMatchSettings`)に進んでいました。既に誰かが
探している対戦にそのまま参加したいだけの人にとってはこの設定入力は
不要な手間になります。オートマッチング配下に「検索する(条件を設定して
探す側)」と「参加する(そのまま入る側)」を分けたサブメニュー
(`_showAutoMatchEntry`)を追加しました。実際の待合ロビーの仕組み
(固定の待合ロビーチャンネルへ参加するだけで、参加が一番早い人が自動的に
リーダー=対戦部屋の作成役になる)は両方で全く同じで、「参加する」は
単に自分の希望条件を設定する画面を経由せず、即座に待合ロビーへ加わる
だけの違いです(もし結果的にリーダーになった場合は、このシーンの
デフォルト設定がそのまま使われます)。

**スマホ対応**: このゲームは矢印キー+Space(キーボード)専用の操作しか
無く、タッチ操作の手段が一切無かったため、スマホでは事実上プレイ不可能
でした。加えて、メニュー画面群(タイトル/対戦設定/オンライン対戦ロビー/
リザルト/ランキング)はデスクトップの横長画面を前提にした固定ピクセル
オフセット(centerX±220px等)でボタン・設定行・テーブルを配置しており、
スマホの狭い画面(360〜430px前後)ではラベルや+/-ボタン・テーブルの列が
画面外に切れてしまっていました。

対応として以下を実装しました。

1. 対戦画面(GameScene)に、画面左下の仮想十字キー(4方向ボタン)・右下の
   爆弾設置ボタン・右上の一時停止ボタンを追加しました。タッチ対応
   デバイス(`'ontouchstart' in window`またはnavigator.maxTouchPoints>0、
   `TouchControlLayout.isTouchCapable`で判定)でのみ半透明のオーバーレイ
   として表示され、デスクトップのマウス/キーボード操作の邪魔をしません。
   ボタンの押下状態は既存のキーボード入力状態とOR条件で判定するため、
   キーボード操作可能な環境ではそのまま従来通り併用できます。
2. 対戦画面右側のプレイヤー情報パネルは、画面が狭い場合にパネル幅が
   実質0になりプレイヤー情報が一切表示されなくなる不具合があったため
   (`ViewportLayout.computeBattleLayout`)、パネル幅は画面がどれだけ
   狭くても最低限(`MIN_HUD_PANEL_WIDTH`)確保するよう修正し、その場合は
   プレイヤーカードをアイコン中心の縦積みレイアウト(コンパクト表示)に
   自動的に切り替えるようにしました。
3. タイトル/対戦設定/オンライン対戦ロビー/リザルト/ランキングの各画面は、
   画面の実サイズから縮小率(0.6〜1.0)を算出する共通関数
   (`ResponsiveUI.computeUIScale`)を新設し、ボタン・設定行のオフセット・
   テーブルの列位置・フォントサイズにこの縮小率を一律で乗算することで、
   スマホの狭い/低い画面でもレイアウト全体が自動的に縮小されて画面内に
   収まるようにしました。デスクトップの標準的な画面サイズでは縮小率が
   ちょうど1になり、従来の座標・見た目と完全に一致します(回帰なし)。

**検証**: 新規`test_round_g.mjs`(50件)を追加。`ResponsiveUI.
computeUIScale`・`TouchControlLayout.computeTouchControlLayout`/
`isTouchCapable`の純粋関数としての検証に加え、偽Phaser環境上で実際に
`GameScene`をタッチ対応/非対応それぞれの条件でインスタンス化し、(a)
タッチ非対応では仮想ボタンが作られないこと、(b)タッチ対応では例外なく
作られること、(c)仮想十字キー/爆弾ボタンの入力が既存のキーボード入力・
ネットワーク入力メッセージと正しくOR条件でマージされること、(d)狭い
画面でプレイヤーカードがコンパクトレイアウトに切り替わることを確認して
います。`OnlineLobbyScene`についても、実際のクラスをインスタンス化して
`_showModeSelect`→`_showAutoMatchEntry`→`検索する`/`参加する`/`戻る`の
各ボタンのクリックハンドラが意図した遷移先を呼び出すことを直接検証
しました。

このサンドボックス環境には実際のブラウザ/スマホ実機が無いため、実際の
タッチ操作の感触(ボタンの大きさ・配置・反応速度)やレイアウトの見た目は
実機での確認が必要です。特にiPhone/Androidそれぞれの実ブラウザでの
表示崩れの有無、仮想十字キーの操作性(斜め入力の扱い等、現状は上下左右
の単純な4ボタンのみで斜め移動は非対応)は実機確認をお願いします。

### 2026-07更新: スマホ画面に面がおさまるように調整・AI難易度を少し緩和・横壁からも面をまたげるように変更

**報告内容**: 「スマホ用の画面に面がおさまるようにして。AIのレベルを少し
下げて。各面の4つ角からほかの面に移動できるようにじゃなく、横壁に壊せる
ブロックを設置おねがい」

**スマホの画面に面がおさまるように**: 対戦画面の3Dステージ(`CubeRenderer`)
は固定位置のカメラを使っており、Three.jsの`PerspectiveCamera.fov`は
「縦方向の視野角」を表す。そのためfov・カメラ距離を固定したまま、右側
HUDパネル分を差し引いた3D描画領域のアスペクト比(幅/高さ)だけが変わると、
スマホの縦長画面(特に幅の狭い機種でHUDパネルの最低幅を確保した結果、
3D描画領域が幅294px×高さ844pxのような極端な縦長になるケース)では横方向の
視野が大幅に狭くなり、サイコロの面の左右が画面からはみ出て見切れて
しまっていた。新設の`CameraFit.computeCameraFit(aspect)`(純粋関数)で、
画面が縦長(aspect<1)になるほど縦方向のFOVを広げて横方向の視野を確保し、
FOVの上限(85°、魚眼レンズのような強い歪みを避けるための上限)に達した後は
カメラを少し後ろに下げる(距離を伸ばす)ことで残りを補うようにした。
横長・正方形の画面(aspect>=1、従来のデスクトップ相当)では調整が入らず、
従来の見た目のまま(回帰なし)。

**AIのレベルを少し下げて**: `AI.js`の`AI_PROFILES`(EASY/NORMAL/HARD/EXPERT
共通)を、判断間隔(`decisionIntervalMs`)を少し延ばす(反応を少し遅く)・
`mistakeChance`(回避を試みない確率)を少し増やす・`bombChance`/
`killShotChance`/`chaseChance`(積極性)を少し下げる、という方向で4難易度
すべて一律に緩和した。難易度間の相対的な強さの順序(EASY<NORMAL<HARD<
EXPERT)は変えていない。

**横壁からも面をまたげるように**: サイコロ6面ステージ(`CubeStage`)は
これまで、各面の外周(perimeter)のうち四隅とその approach マス(隅へ歩いて
近づくための辺沿いの隣接1マス、計8マス)だけを例外的に壊せるブロック
(SOFT)として開放しており、辺の途中(横壁)からは面をまたげなかった。
「各面の4つ角からしか隣の面へ移動できないのではなく、横壁に壊せる

### 2026-07更新: 壊せないブロックの配置を再修正(斜めの隙間・外周の扱い)

**報告内容**: 「壊せないブロックは前後左右斜めも1マス空けないと移動でき
ない。端が全て壊せるブロックになってる。端も全て他のマスと一緒にして」

上の項目で導入したチェッカーボードパターン(`(col+row)%2===0`)は、盤面
全体に密に柱を配置できた一方、チェッカーボードの性質上「柱同士が斜めには
隙間なく連続してしまう」という問題があった(前後左右には必ず1マスの隙間が
あるが、斜め方向の隣接マスは同じ色=柱になる)。またその時点でも、外周
(perimeter)は`Stage._decideBlockType`のisBorder判定により柱パターンとは
無関係に常にHARDにしていたが、CubeStage側の`_openFaceWalls`が生成直後に
外周を全マスSOFT(壊せるブロック)へ強制的に上書きしていたため、実際には
「外周が全て壊せるブロックになっている」状態になっていた。

対応として、柱判定を`col % 2 === 0 && row % 2 === 0`という伝統的な
ボンバーマン配置に戻した。この配置では、どの柱についても縦・横はもちろん
斜めも含めた周囲8マスに別の柱が存在せず、前後左右斜めいずれの方向にも
必ず1マス以上の隙間ができることが幾何学的に保証される。あわせて、外周を
別扱いしていた2つの処理(`Stage._decideBlockType`のisBorder特別扱い、
`CubeStage._openFaceWalls`による外周の強制SOFT化)を両方とも撤廃し、外周も
内側のマスと全く同じ柱判定・ランダム配置ロジックに従うようにした
(「端も全て他のマスと一緒にして」への対応)。結果として、外周のおよそ
半分(柱パターンに一致する側、四隅を含む)は柱のまま残り、残り半分は内側と
同様にランダムに空白/壊せるブロック/アイテムになる。面をまたぐ移動は、
この「壊せる/空白になった外周マス」を経由して行うことになる(四隅そのもの
は今回の変更で恒久的に柱=壊せない扱いになったため、四隅ちょうどからの
面またぎはできなくなったが、その両隣の横壁マスは引き続き壊せる/空白に
なりうるため、面をまたぐ手段自体は失われない)。

**検証**: `test_phase1.mjs`の外周検証を「柱(col・rowが共に偶数)のみが
HARDになる」「柱同士は8方向いずれにも隣接しない」という新しい不変条件に
更新し、`test_cube.mjs`の3b/3c(サイコロ面の外周・連動破壊)、
`test_round_i.mjs`(横壁対応の静的確認)、`test_round_j.mjs`(今回の一連の
要望対応の検証)も、外周が内側と同じルールに従うこと・四隅は恒久的に柱で
あること・柱同士に必ず1マス以上の隙間があることを検証するよう更新した。
既存の全テストも再実行し、regressionが無いことを確認済みです(合計447件
全パス)。

このサンドボックス環境には実際のブラウザ・スマホ実機が無いため、実際の
マップの見た目(柱の密度感・外周の壊せる箇所の見え方)は実機・実ブラウザ
での確認が必要です。

## Renderへのデプロイ

ビルド不要な静的サイト（Phaser CDN読み込み + ES Modules）なので、
Renderの「Static Site」で十分動きます。

1. Render ( https://dashboard.render.com ) にログイン
2. 「New +」→「Static Site」を選択し、GitHubの `kumacchi-bomb` リポジトリを接続
3. 設定項目:
   - Build Command: 空欄のままでOK（何もビルドしない）
   - Publish Directory: `.`（リポジトリ直下、`index.html`がある場所）
4. 「Create Static Site」でデプロイ完了。数十秒でURLが発行されます。

同梱の `render.yaml` を使えば、「New +」→「Blueprint」からリポジトリを
選択するだけで上記設定が自動適用されます。
